# 愿景与范围 v1.0｜CampusBuddy

状态：**设计阶段，系统尚未实现。** 六人、十周、课程验收版本。

## 1. 为什么做

校园里大量结伴需求是临时、小规模、强时效的：晚饭拼桌、晚间跑步、图书馆自习、周末羽毛球、竞赛组队。发起人在班级群里广播一句，消息被闲聊淹没；跨学院几乎触达不到；爽约没有记录。需要的不是又一个社交 App，而是把一次活动对象化：类型、时间、地点、名额、截止、名单、履约。

| 编号 | 问题 | 现有做法的不足 |
| --- | --- | --- |
| P-01 | 临时结伴只能靠群广播 | 无分类、不可检索、无名额 |
| P-02 | 可触达人群通常小于熟人圈 | 无搜索、筛选、推荐 |
| P-03 | 爽约零成本 | 无履约记录 |
| P-04 | 名单和提醒全靠发起人 | 无状态机、无自动通知 |
| P-05 | 广告骚扰无人治理 | 无审核、举报、敏感词 |
| P-06 | 运营没有数据 | 无看板 |

## 2. 愿景陈述

对于希望在学习、运动与生活中快速找到同行者的在校学生，CampusBuddy 是面向本校的即时结伴平台。用户应能在一分钟内发布结构化搭子活动，系统把活动推到合适的人面前，并用可追溯的信用分保证说到做到。

三句话自测是否落地：陌生同学能否在三分钟内找到今晚仍开放、且在本人校区的自习搭子；连续爽约者能否被限制发布；管理员能否看出本周哪类活动报名转化最高。

## 3. 范围内 / 范围外

| 在 V1.0 内 | 不在 V1.0 内 |
| --- | --- |
| 微信登录 + 账号密码登录、JWT、RBAC | 在线支付、资金托管 |
| 活动发布、筛选、报名、成团 | WebSocket 即时通讯 |
| 敏感词 + 审核 + 举报 | 跨校与社会用户 |
| 信用分流水与限制策略 | 校园卡/闸机对接 |
| 可解释推荐（规则打分，UserCF 可裁剪） | 自建或调用付费大模型 |
| Web 用户端、小程序、管理后台 | 持续后台定位 |

后续版本可以补群聊、固定圈子和更重的推荐模型，不构成本期承诺。

## 4. 目标与成功标准

课程目标：十周可演示闭环；有效代码行不低于 10000（去空行去注释，不含生成代码与依赖）；P0 需求通过测试。

| 编号 | 标准 | 目标值 | 口径注意 |
| --- | --- | --- | --- |
| SC-01 | P0 功能 | 100% 测过 | 跟踪矩阵 |
| SC-02 | 有效代码行 | ≥10000 | cloc 分模块 |
| SC-03 | 推荐位报名转化 | ≥自然列表 1.2 倍 | 造数或内测，须标明样本 |
| SC-04 | 核心查询 P95 | ≤300ms；推荐目标 ≤60ms | 压测后才报告，不预填 |
| SC-05 | 到场率 | 接入信用后 ≥85% | 仅测试数据，不称真实校园 |
| SC-06 | 发布 ≤5 步、报名 ≤3 步 | 演示走查 | |
| SC-07 | 干净环境 30 分钟可部署 | Docker Compose | |

## 5. 用户与角色

| 角色 | 主要权限 | 限制 |
| --- | --- | --- |
| 游客 | 浏览公开活动 | 不可报名、不可看联系方式 |
| 普通用户 | 发布、报名、评价、举报 | 每日发布 ≤3；信用低于阈值受限 |
| 社团账号 | 批量发布、名单导出、置顶申请 | 需管理员认证 |
| 内容审核员 | 审核、敏感词、举报 | 不能删库级用户数据 |
| 超级管理员 | 角色、参数、看板、日志 | 操作留痕，不可注销自身 |

发起型约 20%、参与型约 65%、社团约 10%、管理员约 5% 是产品假设，不是本校调查结果。本校调查见市场调研中的待做项。
