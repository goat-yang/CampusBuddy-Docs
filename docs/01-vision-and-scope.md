# 愿景与范围 v1.0｜CampusBuddy

状态：**与愿景 V1.5、需求规格 V1.5 对齐，可以开始实现。** 六人、十周、课程验收版本。

## 1. 为什么做

校园里大量结伴需求是临时、小规模、强时效的：晚饭拼桌、晚间跑步、图书馆自习、周末羽毛球、竞赛组队。发起人在班级群里广播一句，消息被闲聊淹没；跨学院几乎触达不到；爽约没有记录。需要的不是又一个社交 App，而是把一次活动对象化：类型、时间、地点、名额、截止、名单、履约。

| 编号 | 问题 | 现有做法的不足 |
| --- | --- | --- |
| P-01 | 临时结伴只能靠群广播 | 无分类、不可检索、无名额 |
| P-02 | 可触达人群通常小于熟人圈 | 无搜索、筛选、推荐 |
| P-03 | 爽约零成本 | 无履约记录 |
| P-04 | 名单和提醒全靠发起人 | 无状态机、无自动通知 |
| P-05 | 广告骚扰无人治理 | 无审核、举报、敏感词 |
| P-06 | 运营没有数据 | 无看板 |

## 2. 愿景陈述

电梯测试用下面六行。

| | |
| --- | --- |
| FOR | 上海大学在校学生，先服务找晚饭、自习、运动搭子的本科生 |
| WHO | 临时结伴靠群消息，跨学院叫不到人，爽约没有记录 |
| THE | 校园搭子是一个面向单一学校的活动工具（微信小程序和网页） |
| THAT | 当天找到今晚、本校区、仍有名额的一场局，不到场留下信用记录 |
| UNLIKE | 班级群、配人的社交产品、嵌在社区里的组局、没有学号和校区的城市报名工具 |
| OUR PRODUCT | 只做本校、本校区、带名额、截止和信用流水的这一场活动 |

三句话自测：已绑定学号的同学能否在 3 步、1 分钟内报上一场本校区、仍有名额的局；推荐失败时首页是否仍有可报名的热门列表；逾期未确认的报名是否停在待结算，而不是被记成全部到场。

## 3. 范围内 / 范围外

| 在 V1.0 内 | 不在 V1.0 内 |
| --- | --- |
| 上大学号/工号 + 本平台密码；首次学校邮箱验证码；JWT、RBAC | 在线支付、资金托管 |
| 微信登录作小程序预览兜底（须绑定学号后才能报名） | 在页面上收集学校统一认证密码；未批准的 SSO 模拟登录 |
| 活动发布、筛选、报名、成团 | WebSocket 即时通讯 |
| 敏感词 + 审核 + 举报 | 跨校与社会用户 |
| 信用分流水与限制策略 | 校园卡/闸机对接 |
| 热门列表（P0）；加权打分与理由（P1）；协同过滤可以裁 | 自建或调用付费大模型 |
| Web 用户端、小程序、管理后台 | 持续后台定位 |

后续版本可以补群聊、固定圈子和更重的推荐模型，不构成本期承诺。

已定规则：审核通过后进入报名中，不单设「已发布」。报名默认自动通过并占名额；只有该活动打开「需要确认」才进入待确认，且不占正式名额。逾期未确认保持待结算，不加分也不扣分。

## 4. 目标与成功标准

十周内交付可演示的完整系统；文档能从问题追踪到需求和验收；全部 P0 在演示中走通。步骤、性能和信用规则见需求规格，不用代码行数衡量。

| 编号 | 标准 | 目标值 | 口径 |
| --- | --- | --- | --- |
| SC-01 | 功能完整 | P0 全部实现并通过测试 | 需求跟踪与测试记录 |
| SC-02 | 可交付 | 文档、部署和演示能够复现 | 交付清单 |

## 5. 用户与角色

| 角色 | 主要权限 | 限制 |
| --- | --- | --- |
| 游客 | 浏览公开活动 | 不可报名、不可看联系方式 |
| 普通用户 | 发布、报名、评价、举报 | 每日发布 ≤3；信用低于阈值受限 |
| 社团账号 | 批量发布、名单导出、置顶申请 | 需管理员认证 |
| 内容审核员 | 审核、敏感词、举报 | 不能删库级用户数据 |
| 超级管理员 | 角色、参数、看板、日志 | 操作留痕，不可注销自身 |

发起型约 20%、参与型约 65%、社团约 10%、管理员约 5% 是产品假设，不是本校调查结果。本校调查见市场调研中的待做项。
